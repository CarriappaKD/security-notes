# Module 4: Network Traffic and Logs Using IDS and SIEM Tools

## Logs

A **log** is a record of events occurring within an organization's systems; each **log entry** details a single event on a device/system. Originally used just for troubleshooting (e.g., error logs explaining why something failed), logs are now central to security investigations — they help answer the **five W's**: who, what, when, where, why.

Security teams typically access logs through **logging receivers** like SIEM tools, which consolidate logs into a central repository and support **log analysis** (examining logs for events of interest).

### Common Log Types

| Type | Generated By |
|---|---|
| **Network** | Firewalls, routers, switches |
| **System** | Operating systems (Windows, Linux, macOS, Chrome OS) |
| **Application** | Software applications (e.g., a smartphone app) |
| **Security** | Antivirus, IDS, and similar tools — e.g., file deletion events |
| **Authentication** | Any authentication event — e.g., a successful login |

### Log Detail and Verbosity

A basic log entry includes date, time, location, action, and author:
```
Login Event [05:45:15] User1 Authenticated successfully
```

**Verbose logging** records additional detail beyond the default:
```
Login Event [2022/11/16 05:45:15.892673] auth_performer.cc:470 User1 Authenticated successfully from device1 (192.168.1.2)
```

## Log Management

**Log management** is the process of collecting, storing, analyzing, and disposing of log data.

### What to Log

Depends on the organization and its event of interest — overly verbose sources may need to be tuned down. Note: data like phone numbers, emails, and names count as **PII** and may require special handling (or be restricted from logging entirely in some jurisdictions).

### The Problem with Overlogging

Logging *everything* is a common mistake. Downsides:
- Increased storage/maintenance costs
- Higher system load, hurting performance and usability
- Makes it harder to search for and identify genuinely important events

### Log Retention

Regulated industries may require retaining logs for set periods:
- **Public sector** — FISMA (Federal Information Security Modernization Act)
- **Healthcare** — HIPAA
- **Financial services** — PCI DSS, GLBA (Gramm-Leach-Bliley Act), SOX (Sarbanes-Oxley Act)

### Log Protection

Storing logs on a **centralized log server** (rather than locally on the originating device) maintains integrity — it puts a barrier between an attacker and the log data itself, making tampering harder.

## Log Formats

Understanding log format syntax is essential for reading logs accurately during investigations.

### JSON (JavaScript Object Notation)

Lightweight data format commonly used in web technologies and cloud environments.

| Syntax Element | Role |
|---|---|
| **Key-value pair** | A key, colon, and its value — e.g., `"Alert": "Malware"` |
| **Commas** | Separate multiple data items |
| **Double quotes** | Enclose string (text) data; numbers are unquoted |
| **Curly brackets `{}`** | Enclose an **object** — a comma-separated list of key-value pairs |
| **Square brackets `[]`** | Enclose an **array** — a comma-separated ordered list, e.g., `["Administrators", "Users", "Engineering"]` |

```json
"User":
{
    "id": "1234",
    "name": "user",
    "role": "engineer"
}
```

### Syslog

A standard with three related meanings:

1. **Protocol** — transports logs to a centralized server (port 514 plaintext, port 6514 encrypted)
2. **Service** — forwards logs from multiple sources into one location
3. **Log format** — native to Unix systems; made up of a **header**, **structured-data**, and a **message**

**Example:**
```
<236>1 2022-03-21T01:11:11.003Z virtual.machine.com evntslog – ID01
[user@32473 iut="1" eventSource="Application" eventID="9999"]
This is a log entry!
```

| Part | Contains |
|---|---|
| **Priority (PRI)** `<236>` | Urgency of the event — generally, *lower* number = *more* urgent |
| **Header** | Timestamp (`2022-03-21T01:11:11.003Z` — date, `T` separator, 24-hr time with milliseconds, `Z` = UTC), hostname (`virtual.machine.com`), application (`evntslog`), message ID (`ID01`) |
| **Structured-data** | Key-value pairs in brackets, e.g., `[user@32473 iut="1" eventSource="Application" eventID="9999"]` |
| **Message** | The actual log message — `This is a log entry!` |

### XML (eXtensible Markup Language)

Native file format on Windows systems.

| Element | Role |
|---|---|
| **Tags** | Start/end pairs — `<tag>` ... `</tag>` |
| **Elements** | Data + its tags; every document needs a root element, which can contain child elements |
| **Attributes** | Extra info inside the tag itself, always quoted — e.g., `<Data Name='SubjectUserSid'>S-2-3-11-160321</Data>` |

```xml
<Event>
    <EventID>4688</EventID>
    <Version>5</Version>
</Event>
```
`<Event>` is the root element; `<EventID>` and `<Version>` are its child elements.

### CSV (Comma Separated Value)

Values are comma-separated; field *position* corresponds to a field name, but the names themselves usually aren't included in the log — you need to know the source device's field order to interpret it.

```
2009-11-24T21:27:09.534255,ALERT,192.168.2.7, 1041,x.x.250.50,80,TCP,ALLOWED,1:2001999:9,"ET MALWARE BTGrab.com Spyware Downloading Ads",1
```

### CEF (Common Event Format)

Key-value-structured format with a defined field order:
```
CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|Severity|Extension
```

## Telemetry vs. Logs

**Telemetry** is the broader collection/transmission of data for analysis (e.g., packet captures), while **logs** specifically record discrete events. Both are critical evidence sources for investigating suspicious activity.

## IDS Technologies: HIDS vs. NIDS

| Type | What It Monitors |
|---|---|
| **HIDS** (Host-based IDS) | Installed as an agent on a single host/endpoint; monitors internal activity (file systems, resource usage, user activity, inbound/outbound traffic) for unauthorized/abnormal behavior |
| **NIDS** (Network-based IDS) | Installed at specific points in the network; inspects traffic across multiple devices for malicious activity |

Using both together gives a multi-layered, complementary view of host-level and network-level activity.

### Detection Techniques

| Technique | How It Works | Advantages | Disadvantages |
|---|---|---|---|
| **Signature-based analysis** | Compares activity against known malicious patterns ("signatures") — e.g., specific byte sequences, IPs, malware scripts | Low false-positive rate — very efficient at catching *known* threats | Signatures can be evaded by modifying attack code; requires constant updates; can't detect unknown threats (new malware, zero-days) |
| **Anomaly-based analysis** | Two phases: **training** (establish a baseline of normal behavior) and **detection** (flag activity outside that baseline) | Can detect new/evolving, previously unknown threats | High false-positive rate (any deviation gets flagged, even benign); an attacker present *during* training gets baked into the "normal" baseline, potentially hiding a pre-existing compromise |

## Suricata

An open-source IDS/IPS/network analysis tool, usable in three modes:

| Mode | Function |
|---|---|
| **IDS** | Monitors network (or host) traffic and alerts on suspicious activity |
| **IPS** | Detects *and* blocks malicious activity (requires enabling IPS mode) |
| **NSM** (Network Security Monitoring) | Analyzes live traffic or existing captures, and creates/saves packet captures — useful for forensics, incident response, and refining signatures |

- Configuration/rule files live in `/etc/suricata/rules` on Linux; custom rule files (e.g., `custom.rules`) use `#` for comments.

### Suricata Log Types

| Log | Captures |
|---|---|
| **Alert logs** | Events triggered by a detection signature — event type, source/destination IPs, protocol, signature ID/message |
| **Network telemetry logs** | General traffic flow activity, alert-triggering or not — e.g., an HTTP event's hostname, user agent, content type |

### Rules (Signatures)

A Suricata rule/signature has three parts:

| Component | Role |
|---|---|
| **Action** | What to do on a match — `alert`, `pass`, `drop`, `reject` |
| **Header** | Traffic details — source/destination IP, ports, protocol, direction |
| **Rule options** | Additional customization for the signature |

**Custom rules** are strongly recommended over relying only on pre-written ones — tailoring detection to your environment reduces false positives.

### Configuration and Log Files

- `suricata.yaml` — the main configuration file, written in YAML
- `eve.json` — detailed event/alert metadata in JSON, including a `flow_id` for correlating related events to one network flow; preferred for deep analysis and SIEM ingestion
- `fast.log` — minimal alert info (IP/port basics); legacy format, not suited for incident response or threat hunting

## SIEM Tools (Revisited)

The SIEM process has three steps:

1. **Collect and aggregate data** — pull event data from multiple sources
2. **Normalize data** — convert to a consistent, structured, searchable format (normalization capability varies by SIEM tool)
3. **Analyze data** — organize/index the data, then correlate it to surface patterns of unusual activity

### Log Ingestion

**Log ingestion** = collecting and importing log source data into the SIEM. The SIEM stores a *copy* of the event data, so analysis never modifies the original source logs — giving analysts a centralized place to investigate and respond.

### Log Forwarders

Manually uploading logs doesn't scale across thousands of devices, so organizations typically use **log forwarders** — software that automates collecting and sending log data to a destination like a SIEM. Some OSes have native forwarders; otherwise, third-party forwarding software is installed and configured to specify which logs go where.

## Searching in SIEM Tools

### Splunk (SPL — Search Processing Language)

```
index=main fail
```
- `index=main` — retrieve events from the `main` index (where Splunk stores processed event data)
- `fail` — the search term; returns events containing "fail"

**Pipes (`|`)** chain commands, feeding one command's output into the next:
```
index=main fail | chart count by host
```
- Finds events matching "fail" in `main`, then charts the count of matches **by host** — useful for spotting hosts with excessive failures.

**Wildcards (`*`)** expand a search to match variations:
```
index=main fail*
```
Matches "fail", "failed", "failure", etc.

> Use double quotes for an exact phrase match, e.g., `"login failure"` — matches only that exact phrase, not "failure" or "login" separately.

### Google Security Operations (Chronicle)

Two search types:

| Search Type | How It Works |
|---|---|
| **UDM Search** (Unified Data Model) | Default search — queries ingested, parsed, and **normalized** data; faster since it searches structured/indexed data. UDM events include common fields: **Entities** (nouns — device/user/process context), **Event metadata** (event type, timestamps), **Network metadata** (protocol/network details), **Security results** (security outcomes, e.g., "virus detected and quarantined") |
| **Raw Log Search** | Searches raw, unparsed logs when normalized data doesn't have what you need — slower, but supports regular expressions for precise pattern matching |

**Example UDM search** (find login events):
```
metadata.event_type = "USER_LOGIN"
```
